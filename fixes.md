# Cloesce Fixes

## 1. Should be able to format a specific file or directory with cloesce fmt
Right now cloesce fmt doesn't accept a file argument. It should accept an optional one such that we can call it like:

```bash
cloesce fmt examples/realworld/src/api/article.ts
```

It could accept a directory as well, in which case it would format all files in that directory and its subdirectories:

```bash
cloesce fmt examples/realworld/src/api
```

By default, if excluded, it uses the cloesce.jsonc config files src dir.

```bash
cloesce fmt
```

## 2. CRUD declarations fixed order

It seems that CRUD declarations in a Data Source require a fixed order in the parser. We should be able to declare in any order:

```cloesce
source Foo for Bar {
    get {}
    list {}
    save {}
    // ... any combination of get, list, save
}
```

## 3. Navigations Missing Undefined

A one-to-one navigation property is not properly given the `| undefined` type on the backend generated code. Every single 1:1 should have this because it may not be included. 1:M doesnt need it because it is always an array, even if empty.

## 4. DO KV reads need undefined or null

Durable Object KV values can return `| undefined | null` but the generated code types it as if it cannot be undefind or null. Fix the generated code to reflect the reality of DO KV reads.

for example:

```cloesce
durable Foo {
    bar -> int {}
}

model Baz {
    kv Foo::bar {
        qux
    }
}
```

when generated to an interface, it should be:
```ts
interface Baz {
    qux: number | undefined | null;
}
```

anywhere else that references this should follow suite.

The easiest fix would be wrapping the type for `qux` in `CidlType::Option` **in the compiler**, which we should ensure is `undefined | null` in the generatd TypeScript code EVERYWHERE, not just for this.

## 5. Stubbed CRUD DS methods include plan doc

If a Data Source has a CRUD method that is stubbed out (not should not be generated by the compiler), it includes the plan IR doc in the generated code.

This should be replaced with a simple `/** Custom [method] implementation */` doc, instead of seeming like it calls the default implementation.

Additionally, ensure the compiler doesn't try to generate plans for stubbed methods as we won't use them

## 6. Data Sources missing `ctx`

If a Data Source injects a Durable Object context (e.g. `inject { MyDo::id }`), the generated code for the Data Source methods should include a `ctx` parameter in the `env` argument. Right now it is missing, which makes it impossible to use the injected DO context.

We should test this in the DO e2e test.

## 7. Lowercasing

Right now in the `env` we lowercase the first letter of models, injectables, data sources, etc.

Let's just remove all of that shit, and then fix all e2e/examples/docs that rely on it. It adds a ton of boilerplate and is unnecessary. The generated code should just use the names as they are declared in the schema.


## 8. Env namespace types

given some schema:
```cloesce
db { Db }

r2 MyR2Namespace {}

// ... kv, do, etc
```

If I had some method that accepted just the **upgraded** `Db`, there is no type that would give me all of the upgraded methods generated in cloesce. Same for r2, do, kv and the others. We should be able to do:

```ts
function foo(db: Env.Db) {
    db.Model.get(...) // all upgraded methods should be available
}
```

Ideally this can completely replace the whole `Db_Db` type deal that we are currently generating: `Env` is the source of truth for everything (remove `FullEnv` too, because that is just going to be `Env`).

Goal: One single `Env` to rule them all, `CfEnv` to be the basic cloudflare level env.

## 9. Save Ignores Unique Keys

When saving a record, if the primary key is present the save plan IR will create an `INSERT OR UPDATE` statement. This is great.

However, if the primary key is not present, it will always just make an `INSERT` statement.

This is a problem when one of the keys present is a `unique` key. In this case, we should also do an `INSERT OR UPDATE` statement, because the unique key may already exist in the database.

We should modify the algorithm to account for this. Make a helper on the Model IDL called `unique_keys()` which returns a list of all unique keys (primary keys, any columns that have a unique id) and uses that to determine if we should do an `INSERT OR UPDATE` statement.

- We need tests for this in the ORM
- The `realworld` example should be able to remove the `resolveTags` algrithm it has and just call `.save`

## 10. Immutable Response Headers from DO

```ts
return new Response(res.body, {

```

We should see if our `.run` method can handle this automatically (return a new mutable response if it is immutable).

- Fix the immutable header problem
- Update all examples in the example dir that manually do this
